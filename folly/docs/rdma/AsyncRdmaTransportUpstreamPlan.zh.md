# Folly RDMA 上游沟通与阶段推进计划

日期：2026-11-17。状态：本项目执行路线草案；没有对外发帖或代码实施结果。

**Goal:** 独立交付完整 RDMA transport，同时主动争取 Folly 接收核心实现；必要扩展点获接纳和完整后端获接纳分别记录。

**Architecture:** 后端保持 `AsyncTransport` 字节流边界，eager SEND/RECV 与预授权 bulk WRITE 共用 Session、额度与退休机制。独立库保障交付，完整进入 Folly 是需要维护者单独确认的后续目标。

**Tech Stack:** Folly `AsyncTransport` / `EventBase` / `IOBuf`、公开 rdma-core、Linux verbs/CM；fbthrift/Rocket 单独集成。源码和平台基线在每次实际提交或验证时固定，不把旧本地分支当作最新上游。

提案正文：[完整后端合入提案](AsyncRdmaTransportProposal.zh.md)。本文件管理范围判断、交付物和阶段门槛；代码实现步骤在技术契约与实施范围确认后另行编写。

## 1. 成功标准与范围纪律

| 目标 | 成功标准 | 当前状态 |
| --- | --- | --- |
| 独立交付 | 公开依赖可取得，能够独立构建、测试、版本化发布并由本项目维护 | 只有 RDMA 设计，尚未实现和验证 |
| 通用改动回馈 | 真实缺陷或必要扩展点有独立理由、测试与维护者反馈 | 尚未形成可直接提交的候选清单 |
| 完整后端进入 Folly | Session、数据路径、内存及回收等核心实现实际进入 Folly，并具备约定的工程支持 | 尚未提出正式范围请求，未获接纳 |

只合入 adaptor、hook、测试或 benchmark，不能把“完整后端”标记完成。相关维护者认可方向也不等于承诺最终合并。

当前提案聚焦 RDMA。已有 CXL/ubmem、busy-poll 和 benchmark 研究是独立工作，不打包为这次请求的前置改动或性能证明。

## 4. 阶段 B：先取得范围与承接意见

社区议题首先请求维护者判断完整后端是否适合进入 Folly，避免一开始要求逐行 review 未获范围认可的大包。

议题材料采用提案正文的结构：请求的决定、使用场景、代码范围、架构与契约、待评审风险、验证和维护安排。完整详细设计可作后续附件，但核心请求必须在正文中独立可理解。

按下表记录结果：

| 公开反馈 | 决策与下一步 |
| --- | --- |
| 相关维护者认可完整范围，给出具体 reviewer 和前置条件 | 记录原话与链接，按条件整理技术分歧和第一批实现；不提前声称最终必合入 |
| 建议完整后端长期留外部，仅接收通用改动 | 维持独立交付；完整合入目标标记为当前未获支持；另做必要 hooks 清单 |
| 仅愿意接 adaptor 或依赖外部核心的封装 | 单独记录可接受范围，不能把它算作完整核心已获认可 |
| 要求更多具体材料后再判断 | 只补足所要求的有限设计、原型或验证，不默认扩大为全部实现 |
| 没有实质回复 | 按第 9 节跟进并限制投入；交付主线继续 |

实质支持至少应回答：接收什么、放在哪里、谁 review，以及哪些验证/维护条件是硬门槛。点赞、礼貌回复、CLA/Import Checks、内部导入和外围修复合入都不能替代这些回答。

## 5. 阶段 C：形成补丁清单并逐项决策

清单每行必须填写：仓库、目标上游 SHA、问题/必要性、现有 API 能否解决、代码范围、可独立复现方式、验证要求、依赖关系和上游反馈链接。没有具体问题与验证的项不进入第一批 PR。

| 分类 | 处理原则 |
| --- | --- |
| 现有公开 API 可满足 | 优先使用现有入口，减少长期补丁 |
| 脱离本后端仍成立的缺陷 | 单独修复和验证，可以直接形成小 PR |
| 确有必要的通用扩展点 | 说明至少一个具体使用场景及无扩展点时的限制，先取得接口方向意见 |
| 后端专属状态机、硬件与协议逻辑 | 保持完整交付边界；根据完整范围反馈决定留外部或进入 Folly |
| benchmark、分析与实验配置 | 与核心能力分开，不要求上游先接收全部本地研究资料 |

不要为建立关系制造无关 cleanup。一个 PR 解决一个可独立解释和验证的问题；拆分不能把不可运行的半套后端伪装成独立能力。

现有本地 CXL 分支对 `EventBase`、通知队列和 fbthrift ReplyQueue 的 `ManualPoll` 修改，不自动归为 RDMA 所需 hook。需先证明该需求不能由现有事件/调度入口满足，再单独讨论。

## 6. 阶段 D：按门槛交付完整后端

以下是交付批次，不是已获批准的代码实施任务。eager 可先形成可验证版本，但 bulk、统一预算和安全退休始终属于本提案最终范围。

| 批次 | 主要交付 | 通过门槛 |
| --- | --- | --- |
| D0 契约与结构 | 必要公共 API 与内部模块边界、能力矩阵、资源账本、安全与退出条件 | 关闭语义、idle detach/attach、错误字节数、权限和 provider 退出证明路径明确；需要上游决定的差异已有记录 |
| D1 共同 core 与 eager | Session、DeviceOps、控制面、基础 MemoryDomain/注册 staging、SEND/RECV 和有界内存 | 字节流、额度、回调重入、partial post、超时与退休模型测试；相应 Linux 原生功能测试 |
| D2 预授权 bulk | slot/lease、WRITE_WITH_IMM、统一字节窗口及 RQ credit | eager/bulk 交错、陈旧授权、延迟 CQ、关闭与故障回收全部覆盖 |
| D3 注册 IOBuf | 托管分配、direct SGE、跨线程回收和域寿命 | COW/alias、借用内存 staging、分配取消、注销失败与 quarantine 的可重放测试 |
| D4 fbthrift 集成 | factory/listener、admission、timeout、egress/observer、逐笔 write context | 真实 Rocket parser/codec 集成；unary、streaming、sink、interaction 按实际支持逐项验收 |
| D5 发布与完整合入评审 | 支持矩阵、可复现硬件记录、文档、维护与弃用安排 | 达到维护者确认的条件；由实际合入文件及提交判断完整范围是否达成 |

Folly 与 fbthrift 的改动分别在任务分支和 worktree 中维护、验证和提交。跨仓库依赖明确引用已确认版本；fbthrift 示例获接纳不能替代 Folly 核心范围评审。

## 7. 验证材料怎样组织

### 7.1 无硬件与原生测试分层

无硬件测试复用生产 Session，只替换设备操作边界。验证项目包括顺序前缀、公共 byte/RQ ledger、lease 唯一发布、延迟 DMA、有限 CQ、回调恰好一次、暂停后的控制进展、退出与晚到回收。

原生层另验 QP/CQ/MR、arm/get/ack、错误 WC、partial post 和 provider 的安全退出。模型通过不等于 provider 或硬件通过；公开默认构建不能静默以 fake 后端代替真实启用要求。

### 7.2 不用旧研究替代新后端证据

现有 CXL/ubmem、Netpoll 或 stub 实验与未实现的 RDMA 后端不是同一验证对象。任何复用数据必须注明 workload、route、build、CPU/NUMA 和设备条件。

开展仓库内性能实验时，先遵守该任务工作区适用的 `AGENTS.md` 与性能实验协议，再读取对应 Frontier/EDR，建立新的证据记录。不能将历史受限结果写成新后端收益。

性能记录至少含 client/server revision、构建配置、provider/驱动/固件、机器与 NUMA/绑核、负载方法、重复 run、完成吞吐、P99、CPU 和注册/退休内存。控制连接成本与无效 run 一并保留，不预设必须超过 TCP 的比例。

### 7.3 PR 中的证据

每个 PR 的说明明确触发条件、前后行为、测试命令与结果、跨仓库前提、未覆盖能力及默认路径影响。文档中的拟议测试名称不作为已经存在的可执行命令。

## 8. 第一批 PR 的选择规则

第一批最多并行推进 1–2 个范围独立的候选，以降低 reviewer 和本项目维护负担；这属于本项目投入策略，不是 Folly 的规定。

候选必须满足：

1. 基于最新目标上游确认仍存在问题或能力缺口。
2. 不要求先合入全部后端才能理解或验证。
3. 有明确测试和对现有默认路径的兼容说明。
4. 不是仅为当前原型命名或泄漏设备细节的公共接口。
5. 对新接口已取得相关维护者的具体方向意见，或者被明确要求提交最小实现供评审。

本轮没有确认任何现存补丁已经满足全部规则。下一份实际交付物应是第 5 节定义的清单，而不是直接把现有开发分支包装为上游 PR。

## 9. 跟进、投入边界与重新进入条件

以下时间从实际发布议题或 PR 的工作日开始计算，是本项目管理投入的建议，不是社区 SLA：

- 首次约 7–10 个工作日后，带新增信息或收敛问题跟进一次。
- 再经过 2–3 周仍无实质意见时，最多再做一次明确范围的跟进。
- 约 4–6 周仍没有具体 reviewer 或接口方向，暂停扩大完整上游适配，保留公开材料，独立交付继续。

出现具体负责人、可执行接口意见或明确验收条件后重新评估投入。若反馈不断增加工作量，却始终没有可接受范围，应先请求收敛范围。

没有回复不是接纳，也不是拒绝；记录为“当前未取得承接意见”。若当前仅获 hooks/adaptor 支持，只有维护者重新明确认可完整范围，才恢复完整合入这一投入分支。
